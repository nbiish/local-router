## update — fix/curation-single-provider-deselect
- start: 2026-09-19T22:05:00Z
- agent: orchestrator
- findings:
  1. Symptom reproduced and root-caused: `PUT /api/model-curation` is gated by `evaluateCurationShrink` (>=90% shrink of a >=10-key catalog => block). Deselecting OpenRouter (447 curated models of 466 total) is a 95.9% shrink, so the write returned HTTP 409, was never persisted, and the next page load re-fetched the old server-side selection — the "models keep coming back" report.
  2. Verified empirically: with the single-provider exemption disabled, a 20-of-22 single-provider clear returns 409 instead of 200 (test failure reproduced).
  3. Live config corroborated the scale: `~/.config/local-router/curation-backups/curation-full-2026-09-19T21-58-19-925Z.json` holds 466 keys with 447 openrouter, reason `PUT /api/model-curation (forced)`; the 21:51 snapshot holds 226 keys with 203 zenmux (ratio 0.889 — just under the 0.9 block threshold, so it snapshotted but did not block).
  4. Secondary defect: `refreshProviderEndpointModels({preserveCuration:true})` auto-curated newly discovered models unconditionally, undoing a deliberate full-provider deselect on the next automated refresh.
  5. UI had no recovery path for 409 on the debounced autosave path — the failure was silent (silent:true), so the selection reverted with no visible cause.
- fix:
  - `evaluateCurationShrink`: exempt targeted single-provider edits (providersBefore.size > 1 && removedProviders.size === 1 && remainingProviders.size >= 1) from the block. Whole-catalog wipes still blocked.
  - `refreshProviderEndpointModels`: gate new-discovery auto-curation on the provider having curated keys before the refresh.
  - `layout.ts`: provider "Deselect all" autosaves with `force: true`; 409 responses render an inline "Force Save" button and, on non-silent saves, a confirm() prompt.
  - Safety net retained: `guardCurationReplacement` still snapshots whenever a write removes >= half the catalog.
- verification:
  - `npm run build` clean.
  - New `tests/curation-merge-guard.integration.test.mjs`: single-provider clear 200, whole-catalog wipe 409, forced wipe 200 — passes.
  - Registered the new test in `package.json` `test:integration` (it was untracked and unregistered in the inherited WIP).
  - Full suite `npm run test:integration`: 150/150 pass, 0 fail.

## blocker — AGENTS.md symlink breaks git index operations
- start: 2026-09-19T22:20:00Z
- agent: orchestrator
- findings:
  1. `AGENTS.md` is tracked as a regular file (mode 100644, blob 6d0d7e7) but on disk it is now a symlink to `/d/Code/ainish-coder/AGENTS.md` (created 2026-09-19 17:01).
  2. `git add AGENTS.md` fails: `error: open("AGENTS.md"): Function not implemented` / `unable to index file`.
  3. `git diff --stat` and `git diff HEAD` abort on the same error, so broad diff/stat commands are unreliable until resolved.
  4. Committing explicit paths still works (this session's commit succeeded).
- resolution: NOT a misconfiguration. The symlink target is the canonical, centrally
  governed contract and carries an explicit notice: "THIS AGENTS.md IS A CENTRALLY
  GOVERNED SYMLINK FROM ainish-coder. NEVER EDIT, TRUNCATE, OVERWRITE, OR COMMIT THIS
  FILE IN DOWNSTREAM REPOS. ALL REPOSITORY-SPECIFIC PRD DIRECTIVES & RULES BELONG IN
  llms.txt." The contract states every target repo is deployed as a live symlink and
  downstream repos are write-protected at git level.
- attempted fix (REVERTED): `git rm --cached AGENTS.md` + `/AGENTS.md` in `.gitignore`,
  which would have restored `git diff --stat`. The `.git/hooks/pre-commit` guard
  installed 2026-09-19T15:29 blocks it:
  `[ERROR] AGENTS.md is a protected canonical symlink managed by ainish-coder.
  Modifying or committing AGENTS.md in downstream repositories is forbidden.`
  The guard matches any staged AGENTS.md change, including the deletion, so untracking
  it is not possible without `--no-verify`. Hook not bypassed; the untrack was reverted
  and the index entry restored (blob 6d0d7e7).
- status: UNRESOLVED — the guard and the symlink are both working as designed, but the
  combination leaves `git diff --stat` / `git diff HEAD` permanently aborting with
  `error: open("AGENTS.md"): Function not implemented`, and `git add -A` unusable.
  Needs an operator decision: allow the untrack in the guard, exclude AGENTS.md from
  the guard's match, or accept the limitation and always scope diffs to explicit paths.

## update — fix/curation-seed-repopulation (latent same-class defect)
- start: 2026-09-19T22:24:00Z
- agent: orchestrator
- branch: main (direct commit)
- findings:
  1. `seedCurationDefaultsForProvider()` bailed out only if the provider already had a
     curated key. A provider with zero keys was therefore indistinguishable from one
     never seeded, so `ensureCurationDefaultsForCache()` (reachable via
     `PUT /api/model-curation { activate: true }`) re-populated its entire catalog and
     silently undid a deliberate deselect — the same bug class as the reported symptom.
  2. Reproduced: with the new guard removed, the new test fails at
     "activate must not re-seed a provider the operator deliberately cleared".
- fix:
  - New `operatorClearedProviders: string[]` on the persisted model source config
    (loader defaults to `[]`; backwards compatible with existing files).
  - `reconcileOperatorClearedProviders(previousKeys, nextKeys)` records providers that
    lose every key in an explicit curation write and lifts the mark once a provider has
    any key again. Wired into `PUT /api/model-curation`,
    `POST /api/curation-configs/load`, `deselectProviderCurationKeys` (off-by-default
    refresh), and `ensureCuratedOverrideSelection`.
  - `seedCurationDefaultsForProvider` skips operator-cleared providers.
- verification:
  - `npm run build` clean.
  - New test `curation seeding: a deliberately cleared provider is not re-seeded by
    activate` — passes with the fix, fails without it.
  - Full suite `npm run test:integration`: 151/151 pass, 0 fail.

     `fallback-disabled-execution-plan`, `fallback-disabled-models`, `prompt-caching`)
