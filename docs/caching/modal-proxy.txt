modal-proxy (self-deployed DeepSeek-V4.1-Flash-1017 on Modal) — Prompt/Context Caching
Last verified: 2026-11-20

Overview
  modal-proxy is a private, self-deployed endpoint running on Modal (vLLM
  server, single model):
  https://nbiish--ep-deepseek-v4-1-flash-1017-server.us-west.modal.direct/v1
  It bills as Modal compute (GPU-seconds), not per-token pricing, and has no
  multi-tenant contention — the KV cache serves only this deployment's
  traffic.

  This host replaces the retired GLM-5.3-Flash / Kimi-K3 deployment
  (nbiish--ep-glm-5-3-flash-server.us-west.modal.direct and
  nbiish--ep-kimi-k3-nbiish-server.us-west.modal.direct). Both old hosts now
  answer `404 domain association not found`; verified 2026-11-20.

Authentication
  A Modal Proxy Token: a Token ID / Token Secret pair, `wk-` and `ws-`
  prefixed respectively, joined with a period and sent as a bearer token:
      Authorization: Bearer $MODAL_PROXY_TOKEN_ID.$MODAL_PROXY_TOKEN_SECRET
  or as the separate `Modal-Key` / `Modal-Secret` headers. Proxy tokens are
  NOT interchangeable with Modal API tokens (`ak-` / `as-`).
  local-router reads the pair from the PQC bundle
  (MODAL_PROXY_TOKEN_ID / MODAL_PROXY_TOKEN_SECRET) and joins it in
  src/providers/modal-proxy.ts; MODAL_PROXY_API_KEY is accepted as a
  pre-joined alternative.

  Status 2026-11-20: the pair in the vault is rejected at this host with
  `401 Webhook token not found` (both auth shapes behave identically, so the
  token is revoked or scoped to another environment — not a dialect
  problem). The operator rotates it via `modal workspace proxy-tokens`; the
  code path needs no change once a valid pair is in the bundle.

Mechanism
  Dual inheritance:
  1. Serving layer: vLLM Automatic Prefix Caching (APC) — implicit KV-block
     reuse of token-identical prefixes, enabled by default in current vLLM
     (`enable_prefix_caching=True`). No explicit breakpoint/TTL API.
  2. Model family: DeepSeek-V4.1-Flash is a DeepSeek-family model; DeepSeek's
     hosted API uses automatic server-side context caching. On this
     self-deployment the *engine* mechanics are vLLM's, but the same
     prompt-design guidance applies (stable system prompts, tool
     definitions, and knowledge docs at the head of the message array).

Max configuration
  - Keep the replica warm (scaledown window pinned high in the Modal app) so
    the GPU KV cache survives between turns; this is the only "TTL" lever.
  - Send `prompt_cache_key` (session/conversation id) per request — vLLM
    ignores it, but it keeps behavior consistent with DeepSeek-family
    upstreams and future-proofs proxy layers. local-router also sends the
    same key as `Modal-Session-ID` so a multi-replica deployment routes a
    conversation to one replica.
  - Stable prefix > everything: system prompt + tool defs + long context
    first, then conversation history, then the fresh user turn last.

Limits & thresholds
  - Cache capacity = replica GPU VRAM minus weights/activations (plus CPU
    offload if configured); LRU eviction under pressure.
  - Cache is lost on scale-down, redeploy, or replica replacement. Keep at
    least one warm replica for cache continuity.
  - No documented minimum shared-prefix size for APC itself; benefit grows
    with prefix length.
  - Any token change early in the prompt invalidates the suffix from that
    point.

Pricing
  No cache-hit token discount exists here — billing is Modal GPU compute
  time. Prefix-cache hits directly reduce prefill GPU-seconds and TTFT, which
  is the cost saving on a compute-billed deployment. src/provider-pricing.ts
  therefore records 0/0 per 1M for this row and labels it compute-billed.

Reasoning dialect
  The served model is DeepSeek-family, so src/provider-policy.ts's `deepseek`
  family override supplies `openai-effort` / EFFORT_FIVE
  (`none|minimal|low|medium|high`) — the dialect measured for this family on
  a gateway (ZenMux, 2026-11-07). The provider row itself stays conservative
  (boolean) so a different family deployed here later is not mis-described.
  The operator's sample request uses `reasoning_effort: "high"`, which is
  inside that ladder.

Model addressing
  Two spellings work: the served model id
  `deepseek-ai/DeepSeek-V4.1-Flash-1017`, and the Endpoint hostname
  `nbiish--ep-deepseek-v4-1-flash-1017-server.us-west.modal.direct` (Modal's
  endpoint-integration contract routes on the `model` field). Both are
  registered in src/provider-model-registries.ts.

Maxing recipe
  1. Order messages exactly like DeepSeek's caching guidance: fixed large
     context (system prompt, tools, knowledge docs) first; conversation grows
     behind it.
  2. Keep the deployment warm (min 1 replica / generous scaledown window).
  3. Batch related requests back-to-back to hit the same in-memory KV blocks.
  4. Don't re-send volatile timestamps/IDs inside the stable prefix.

Local-router integration
  The model id contains `deepseek`, so the family override fires: it injects
  `reasoning_effort` for the caller's level and a `prompt_cache_key` per
  conversation. Anthropic-style cache_control blocks are NOT injected (the
  vLLM endpoint has no explicit caching API), and OpenAI 24h retention fields
  are not relevant here — caching is purely the deployment's vLLM APC plus
  prefix stability.
